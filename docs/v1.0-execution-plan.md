# Agent OS v0.6 → v1.0 执行计划

日期:2026-08-16 · 编制基线:`docs/project-status.md`(2026-08-16,v0.6)与既有架构设计
来源:`docs/Agent_OS_v0.6_to_v1.0_Execution_Plan.docx`(已转 Markdown 入库,
并对照仓库实况修正,见 §10)

从"多租户分布式控制面"推进到"可稳定发布的 Agent 系统软件层"。

- **当前基线**:v0.6 Multi-tenant Scale & Capacity Evidence 已完成
  (1,000 Task 全流水线约 40 tasks/s,双实例并发回归通过;Go 单测、race、
  集成套件与 Linux 交叉编译均通过)。
- **计划周期**:建议 8–10 周(可按团队资源并行压缩;v0.7 可接受滑到 3 周)。
- **核心主线**:Linux 真机验证 → 分片与规模化 → Agent 标准接入 → v1.0
  稳定化。
- **发布目标**:Stable API / 安全边界 / SLO / 兼容性与可重复验收。

## 1. 当前状态与计划原则

v0.6 已交付:控制面生命周期、准入、调度、恢复、预算、配额、池健康、
审计、Memory、工具/模型网关,以及 Go / Wasmtime / OCI-gVisor 运行时。
现阶段不再以"继续堆功能"为主,而是把已实现能力做成可验证、可扩展、
可兼容、可发布的系统。

已验证基线:1,000 Task 全流水线约 40 tasks/s,双实例并发回归通过;Go
单测、race、集成套件与 Linux 交叉编译均通过。

关键边界:runsc/containerd 的 ctr 命令面、seccomp/capability drop/只读
rootfs、Firecracker KVM 尚未在 Linux CI 真机逐项闭环;跨实例按
pool/tenant 分片尚未实现。

计划原则:

- 先解锁真实运行环境,再做大规模证据;
- 是否引入 Kafka/ClickHouse 必须由 1 万～10 万任务容量数据决定,不提前
  复杂化;
- **全局 guardrail:v0.7–v0.8 期间不新增功能面**,只做真机化、规模化与
  证据;任何并发/分片优化必须先通过现有 fencing、outbox、quota、result
  一致性回归。

## 2. v1.0 目标

v1.0 的目标不是"功能最多",而是形成一套稳定的 Agent 运行契约:第三方
Agent 可以在不修改 Kernel 的前提下接入、被调度、获得受控资源、持久化
状态、恢复执行并被审计。

- **运行真实**:OCI/gVisor 与 microVM 边界在 Linux CI/真机环境可重复验证。
- **扩展真实**:多实例控制面支持 tenant/pool 分片,并完成 1 万与 10 万级
  任务容量基线。
- **接入标准**:形成 Agent Manifest / Runtime Interface / Adapter 规范,
  Kernel 不感知具体框架。
- **治理稳定**:身份、权限、预算、审计、配额、恢复与失败默认拒绝形成
  稳定契约。
- **发布稳定**:冻结 v1 API/协议,定义 SLO、兼容矩阵、升级策略、
  Conformance 测试与发布门禁。

## 4. 阶段执行计划

### 4.1 v0.7:Linux Runtime 真机验证

目标:把当前"协议与逻辑已验证"的 Runtime 能力,升级为 Linux 主机上的
可重复真实执行证据。

- **扩展现有 Linux CI**(`.github/workflows/ci.yml` 已存在:buf lint+diff、
  gofmt/vet/govulncheck、`-race` 单元与集成套件、Rust 1.97.1 全链、OCI
  二进制构建并上 PATH 且已预留 `AGENTOS_OCI_CONTAINERD_NAMESPACE` 挂载
  点;本阶段是扩展,不是新建):
  - 新增 Linux 真机腿 job:固定 containerd / runsc 版本(沿用现有 digest
    钉版本风格),启动 containerd + runsc;
  - 启用 OCI conformance 腿(`AGENTOS_OCI_CONTAINERD_NAMESPACE`),验证
    镜像 digest、签名/SBOM 准入、CPU/Memory 限额、stdout spool、孤儿
    容器回收;
  - 输出环境指纹(内核、containerd、runsc、KVM)并保存为 CI 产物。
- **安全隔离**:逐项验证 seccomp、capability drop、只读 rootfs、网络/
  文件系统边界与默认拒绝路径(验收矩阵见
  `deploy/ci/runtime-matrix.md`;注意:当前 ctr 命令面只显式传
  `--cpu-quota`/`--memory`/只读 bind/tmpfs 尺寸,seccomp 与 capability
  drop 依赖 runsc 默认 profile,必须真机复核并决定是否显式传参)。
- **恢复链路**:真机验证 lease 心跳、checkpoint、worker 失联、接管恢复、
  Result-before-success 与 fencing。
- **Firecracker**:先完成 KVM 可用性探测与最小 smoke;高风险 Agent 的
  microVM 正式接入可在 v1.0 前按验收结果决定(P2,不阻塞主路径)。

验收标准:

- Linux CI 中 OCI/gVisor runtime-control / security / recovery 套件可
  重复全绿;
- 所有隔离项都有正向与负向测试;失败路径保持 fail-closed;
- CI 输出固定版本矩阵与日志,可复现到同等 Linux 主机。

> 注:GitHub 托管 runner 无 /dev/kvm,Firecracker 探测在该环境应明确
> 报告 KVM 不可用并跳过真实 smoke;自托管带 KVM 的 runner 才执行完整
> smoke。两条路径都要在 CI 中可重复。

### 4.2 v0.8:跨实例分片与规模化证据

目标:证明 Agent OS 不仅"多实例安全并存",而且可以在多租户高负载下
水平扩展。

- 实现按 tenant / pool 的调度分片策略(**ADR-016**,落 `docs/adr/016-*.md`),
  并保持现有 claim、lease、fencing 与 outbox 语义不被破坏——现有
  `TestDualControllerInstancesAdmitEachTaskExactlyOnce` 与
  `TestDualOutboxDispatchersPublishEachEventExactlyOnce` 即验收断言,
  分片实现后必须继续全绿。
- 构建多租户压力模型:不同租户并行提交、不同配额、热点 pool、worker
  抖动、重试与取消混合负载。
- 容量基线分两档:10,000 Task 先定位数据库/调度/事件瓶颈;100,000 Task
  再验证扩展曲线。**注意时间成本**:当前单机 ~40 tasks/s,100k 需 40
  分钟以上——固定机器规格 + 记录环境指纹,并预留 batch/parallelism
  调参档位(沿用 `AGENTOS_CAPACITY_TASKS` 与容量基线测试的扩展)。
- 记录吞吐、p50/p95/p99、DB lock wait、outbox lag、scheduler retry、
  quota reject、pool saturation 等指标。
- 根据证据做中间件 ADR(**ADR-017**,落 `docs/adr/017-*.md`):只有当
  Postgres/NATS 成为明确瓶颈时,再决定 Kafka、ClickHouse 或其他组件。
- 强化配额:设计 reservation/release-on-completion;评估结算期硬停是否
  进入 v1.0。

验收标准:

- 双实例以上分片压力下,不重复准入、不越权、不丢事件、fencing 违规为 0;
- 完成 10k 与 100k 容量报告,并能明确指出首要瓶颈及是否需要新增中间件;
- 多租户配额在高并发下具备可解释、可审计行为。

### 4.3 v0.9:Agent 标准接入层

目标:把"异构 Agent"从架构定义变成可验证的产品能力。

- 冻结 Agent Manifest:identity、version、runtime、entrypoint、
  capabilities、resource limits、budget、checkpoint、tool/model/memory
  权限。
- 定义 Runtime Interface:start / stop / health / checkpoint / restore /
  event / result 等最小稳定契约。
- 提供 Adapter SDK:优先覆盖 Native Go、Python Remote/A2A、一个主流框架
  Adapter(如 LangGraph)三条路径。
- 统一 capability 映射:Agent 不能直接绕过 Kernel 访问模型、Memory、
  工具或密钥。
- 补齐开发者体验:CLI 初始化/打包/签名/发布/运行/日志;Registry 与
  AgentVersion 对接;提供最小示例项目。
- 建立 Conformance Suite:任何第三方 Runtime/Adapter 通过同一套生命周
  期、权限、恢复与结果一致性测试。
- **API 提升草案**:当前 kind/proto 均为 `v1alpha1`;本阶段启动
  v1alpha1 → v1 提升草案(兼容策略、弃用窗口、conformance 冻结),不要
  拖到 v1.0 才定。

验收标准:

- 至少 3 类 Agent 接入路径可在不修改 Kernel 的情况下安装并执行;
- Adapter 通过统一 Conformance Suite;Kernel 对框架细节零依赖;
- Agent 的模型、工具、Memory、Secrets 访问均经过统一 Gateway/Policy。

### 4.4 v1.0:稳定化与正式发布

目标:从"工程可运行"升级为"接口稳定、故障可控、安全可审计、升级可
管理"的 Release Candidate。

- 冻结 /v1 API、proto 与核心对象语义;定义兼容策略与弃用窗口。
- 定义 SLO:Control API 可用性、调度延迟、任务恢复时间、事件发布延迟、
  审计完整性等——**测量基于仓库已有 OTel + Prometheus/Grafana/Tempo/
  Loki dev 基建**,不新造观测栈。
- HA/Chaos:控制器宕机、NATS 暂时不可用、Postgres failover、worker 丢
  失、网络抖动、重复消息场景。
- 安全加固:SPIRE Workload API 接入优先级确认,镜像/包签名、OpenBao、
  OIDC、mTLS、审计导出做发布门禁。
- 数据生命周期:引用感知 GC 是否进入 v1.0,根据 checkpoint/result/audit
  留存关系做最终 ADR(**ADR-018**,落 `docs/adr/018-*.md`)。
- 发布工程:版本矩阵、迁移回滚策略、升级演练、性能基线、安装文档、
  运维 Runbook、已知限制清单。

验收标准:

- 核心 API/协议不再发生破坏性变更;升级路径和迁移策略可演练;
- 关键 SLO 在标准负载下达到门槛,故障注入后系统能自动恢复或明确失败;
- 安全、容量、兼容、恢复、审计五类 Conformance/验收报告齐全。

## 5. 优先级与依赖关系

| 优先级 | 事项 | 依赖 | 说明 |
|---|---|---|---|
| P0 | 扩展 Linux CI + runsc/containerd 真机闭环 | 无 | 当前多个安全/Runtime 边界的共同前置 |
| P0 | tenant/pool 分片 + 多租户压力 | v0.7 基础稳定 | 决定系统是否具备真实水平扩展能力 |
| P0 | 10k/100k 容量基线 | 分片与压测工具 | 决定是否引入新中间件 |
| P1 | Agent Manifest / Runtime Interface | Kernel 对象模型稳定 | 把"异构 Agent OS"变成标准接入能力 |
| P1 | reservation quota / SPIRE | Linux 环境、身份边界 | 生产治理增强 |
| P2 | 引用感知 GC / 完整 microVM | 前述稳定后 | 除非客户/安全场景要求,否则不阻塞主路径 |

## 6. 核心验收指标

- **正确性**:重复准入 = 0;fencing 违规 = 0;未发布 outbox 事件 = 0;
  Result-before-success 不被破坏。
- **规模**:10k / 100k Task 均有可重复基线;多租户同跑时配额隔离正确。
- **运行时**:Linux 真机 OCI/gVisor 全链路通过;隔离项与恢复项都有负向
  测试。
- **兼容**:至少三类 Agent 接入路径通过同一 Conformance Suite。
- **稳定性**:故障注入后控制面不产生不可恢复的重复执行、状态撕裂或审计
  缺口。
- **发布**:API/proto 兼容策略、SLO、Runbook、迁移/回滚、已知限制齐全。

## 7. 关键风险与控制

- **过早引入重型中间件**:先用 10k/100k 证据做 ADR,避免在没有瓶颈前
  引入 Kafka/ClickHouse。
- **Runtime 真机环境差异**:CI 固定版本矩阵,所有 runtime 测试必须记录
  kernel/containerd/runsc/KVM 信息。
- **Agent Adapter 变成"框架特判"**:只允许 Adapter 依赖框架,Kernel 只
  依赖稳定 Runtime Interface。
- **v1.0 范围膨胀**:P2 项默认不阻塞发布,优先保证正确性、安全、恢复、
  兼容与可观测。
- **性能优化破坏语义**:任何分片/并发优化必须先通过现有 fencing、outbox、
  quota、result 一致性回归。

## 8. 立即执行:前两周任务清单

**第 1 周:Runtime 真机化**

1. 扩展 Linux CI runner job,固定 containerd + runsc 版本并输出环境指纹。
2. 把 runtime-control、OCI provider、security、recovery 测试接入 Linux CI
   真机腿(security/recovery 已在既有 job 中随 `-tags=integration ./...`
   于 Linux 执行;增量是 OCI conformance 腿与指纹)。
3. 补 seccomp / capability drop / readonly rootfs 的自动化正负向测试。
4. 输出第一版 Runtime 验收矩阵和失败项列表。

**第 2 周:闭环 + 分片准备**

1. 修复 Linux 真机失败项,完成 OCI/gVisor 全链路闭环。
2. 完成 Firecracker KVM smoke 与版本/宿主机要求说明。
3. 设计 tenant/pool 分片 ADR(016)与数据模型/claim 变更方案。
4. 准备 10k/100k 压测工具与指标采集模板。

## 9. v1.0 Definition of Done

满足以下条件后,才建议把项目标记为 v1.0:

- Kernel 核心对象、/v1 API、proto 与 Agent Runtime Interface 已冻结;
- Linux 真机 Runtime、安全隔离、恢复接管全部有可重复 CI 证据;
- 10k/100k 与多租户压力报告完成,中间件架构决策有数据支撑;
- 第三方 Agent 可通过标准 Manifest + Adapter 接入,无需改 Kernel;
- HA/Chaos、安全、审计、迁移/回滚、SLO 与 Conformance 均有正式验收结果;
- 文档明确列出未实现边界;任何投影能力都不以"已支持"对外宣称。

一句话主线:先把 Runtime 跑真,再把规模跑大,再把 Agent 接口跑通,最后
冻结契约并做 v1.0 稳定化。
