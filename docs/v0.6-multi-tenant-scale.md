# v0.6 Multi-tenant Scale & Capacity Evidence: 交付文档

日期:2026-08-16 · 状态:完成

v0.6 把多租户规模化面落地:租户级聚合消费配额(窗口限额 + 精确结算 +
准入门)、基于租约心跳的运行时池健康(placement 拒绝失活池)、O6
无放置即释放 claim 并指数退避、双实例控制器与 outbox 并发回归测试、
以及可重复的 1,000 任务控制面流水线容量基线。全部通过构建/单元/
集成/race 验证。

## 1. 租户聚合消费配额(窗口限额)

- 迁移 `000013`:`tenant_quotas`(窗口秒数 + 四维限额,0 = 该维不限,
  与任务预算语义一致)+ `tenant_consumption_windows`(租户 × 固定窗口
  的已结算消费,epoch 对齐,窗口起算点确定)。
- 结算精确:每次新追加的任务预算结算在同一事务内、窗口行锁下累加到
  当前窗口;幂等重放与 delta 结算(先到先得)绝不重复计费;未配置配额
  的租户不跟踪窗口。
- 准入门双层:控制器只读检查产出记录的 `TENANT_QUOTA_EXCEEDED` 拒绝
  决策;`DecideAdmission` 在提交事务内、窗口行锁下原子复检
  (`ErrTenantQuotaExceeded`,不记录任何东西、任务保持 QUEUED),关闭
  只读检查与并发结算之间的竞态。语义:门对已结算消费精确;同一瞬间
  并发准入的突发可能按各自 ceiling 之和短暂超窗,之后窗口关闭直到
  滚动。无预算任务仅在窗口已超限时被拒。
- 控制面 API:`GET/PUT/DELETE /v1/quota` 只作用于认证主体的租户(边界
  由身份而非路径强制),返回配额 + 当前窗口用量。
- 测试:store 单元、控制器单元、API 单元、postgres 集成(精确结算、
  重放/delta 不重计、替换保留、删除停跟踪、准入门、窗口滚动)。

## 2. 运行时池健康:租约心跳新鲜度 → Ready

- `PoolHealthStore.PoolInstanceHealth`:实例仅在"持有未释放且心跳陈旧
  的租约"(已过期,或新鲜度窗口内未续约)时视为失活;空闲实例与已释放
  租约(正常完成或恢复接管)永远健康——恢复机制天然自愈池健康。
- `LeaseAwarePoolSource`:静态池配置叠加租约派生活性,`Ready =
  static.Ready AND 实例存活`;健康结果缺失的实例按失活处理(fail-closed)。
  `Select` 既有的 `POOL_NOT_READY` 拒绝原样生效。
- `cmd/agentos-controller` 默认启用,`-pool-health-freshness`(默认 90s,
  高于租约 TTL 30s)。
- 测试:scheduler 单元(叠加语义、fail-closed、placement 拒绝)与
  postgres 集成(空闲/新鲜/过期/续约/心跳窗口/完成释放/恢复接管)。

## 3. O6:无放置立即释放 claim + 指数退避

- 迁移 `000014`:`tasks.next_schedule_attempt_at`(调度 claim 资格门)+
  `tasks.schedule_retry_count`(退避因子,成功放置归零)。
- `DeferTaskSchedule`:释放调度 claim 与记录退避在同一事务内(claim 立
  即删除,不再等到 TTL),资源版本递增,产出 `TaskScheduleDeferred`
  outbox 事件与审计行;退避状态在任务行上,控制器重启/多实例共享同一
  进度。
- 调度器:无放置时按 `5s × 2^retries`(上限 5 分钟)退避;可重试失败仍
  中止批次,不可重试失败按任务隔离。
- 测试:scheduler 单元(退避、幂次递增、封顶、失败隔离)与 postgres
  集成(claim 门控、deadline、放置重置、fencing、退避递增、outbox +
  审计可观测性)。

## 4. 双实例并发回归(fencing 零重复 / 零丢失)

- `TestDualControllerInstancesAdmitEachTaskExactlyOnce`:两个 admission
  控制器实例(不同 owner ID)竞速同一队列 40 任务,断言每任务恰好被
  准入一次、无遗留 QUEUED、恰有一条 `TaskAdmitted` outbox 事件、无
  残留 claim。
- `TestDualOutboxDispatchersPublishEachEventExactlyOnce`:两个 dispatcher
  竞速同一事件流,断言每个事件恰好发布一次、fencing 拒绝为 0(零重复
  处理)、`published_at IS NULL` 为 0(零丢失)。

## 5. 容量基线(可重复)

- `TestControlPlanePipelineCapacityBaseline`:1,000 任务(可用
  `AGENTOS_CAPACITY_TASKS` 覆盖)在独立 schema(`agentos_capacity`)内
  走完 入队 → 准入 → 调度 → 完成 全流水线;断言全部是计数精确性
  (每任务恰好一个 run/attempt/lease、每生命周期步恰一条 outbox 事件、
  无残留 claim),**不断言墙钟阈值**;每阶段吞吐与 p50/p95/p99 延迟由
  内核时钟时间戳导出并报告。
- 开发机基线(1000 任务):端到端约 40 tasks/s,入队 255/s、准入 215/s、
  调度 209/s、完成 85/s。这是 v0.6+ 中间件决策(是否需要
  Kafka/ClickHouse)的对照证据:当前单 Postgres 控制面已具备的原始
  容量。

## 6. 明确边界(与 v0.5 相同,未变化)

- **SPIRE/workload attestation**(ADR-011 投影):仍为"CA 签发 + 信任束
  分发"模型;SPIRE agent/workload API 接入保持投影。
- **runsc/containerd 真机腿**:ctr 命令面、seccomp/capability drop/只读
  rootfs 等必须接入 Linux CI(containerd + runsc 主机)逐条验证;本机
  (Windows)只验证协议与纯逻辑面。v0.6 未改变该前置。
- **Firecracker/microVM**:仍为文档化边界;验收前置(本清单 Linux CI
  验证、KVM 可用、版本矩阵钉死)未变。
- **配额语义**:准入门对已结算消费精确;并发突发按 ceiling 之和有界
  超窗(文档化);跨窗口消费不回退(窗口内只增)。预留式配额
  (reservation/release)与结算期硬停(settlement-time hard stop)未纳入
  本 slice,记入后续。
